### [2026-09-26] — PRODUCTION LOGIN FIXED: pdf-parse top-level import crashed every serverless request (FUNCTION_INVOCATION_FAILED / 500 on ALL routes) — **by Buffy (Codebuff) for Ram**

- **User ask:** "read full repo and resolve login issue" — login was failing on `https://ncr-oms.vercel.app`.
- **Diagnosis:** production `/health`, `/auth/login`, and even the NEW static-page rewrites (`/payments`, `/inventory`) all returned **500 FUNCTION_INVOCATION_FAILED** — not a credentials problem at all, the whole function was dead on arrival. GitHub deployment statuses showed every recent deploy (up to `8ab7ed6`) as "Deployment has completed / success", so it was a **runtime** cold-start crash, not a build failure. Locally `tsc`/`npm run build`/`vitest` were all clean and a prod-style `node dist/src/server.js` instance logged in fine — the failure only existed under Vercel's **bundled** execution. Reproduced it exactly: `esbuild --bundle api/[...slug].ts` → `require()` → **`ReferenceError: DOMMatrix is not defined`** at module-evaluation time (plus pdf.js's own "Cannot polyfill DOMMatrix/ImageData/Path2D" warnings). Root cause: the pt.7 Meesho-manifest feature added `src/ingestion/meeshoManifestPdf.ts` with a **top-level `import { PDFParse } from "pdf-parse"`** — pdf-parse wraps pdf.js, which touches browser-only globals (DOMMatrix/Path2D/ImageData) while the module is being evaluated; in a bundled serverless build those globals don't exist, so the crash took down the entire app on every request (any request would have done the same — the crash is in module scope, not in a route). Not caught before deploy because local dev (tsx, unbundled) and `node dist/` (unbundled CJS) both have enough Node globals/libuv that pdf.js's evaluation path survives (the polyfill warnings show but evaluation completes), and no test ever *bundled* the API entry.
- **Fix** (`src/ingestion/meeshoManifestPdf.ts`): top-level import → **lazy `await import("pdf-parse")` inside `parseMeeshoManifestPdf()`**, with the full reasoning in a comment. The app now boots without ever touching pdf.js; only an actual manifest-PDF upload loads the engine. This is the same lazy-load pattern browser-oriented libs need on serverless generally — any future native-or-browser-global dependency must be dynamically imported, never top-level, in this repo's serverless entry.
- **Verified:** `npx tsc -p tsconfig.json --noEmit` → 0 errors; `npm run build` clean; the esbuild-bundle repro that crashed before now reports `BUNDLE-REQUIRE-OK`; prod-style compiled instance: `/health` 200, `/auth/login` 200 (real token + company payload), `/orders` 200 authenticated, and `POST /orders/awb-import` with a junk sub-order returned a graceful 207 per-row error (route + its lazy import path healthy end to end); `vitest run tests/ingestion.test.ts tests/security.test.ts` → 18/18.

- **Data-model decision:** parties (APL/Shivam/AK Enterprises/JK) are `suppliers` (Party Master) — **not** warehouses. The existing `purchase_entries`/`purchase_entry_items` (Party Master's pre-existing but bare "Stock In" dialog — SKU/qty/cost/warehouse/party, add-only, no history table, no chalan/GST/bill/payment fields) already modeled exactly this, so this pass extends that table rather than inventing a parallel one. Stock physically lands in the company's real, ledger-tracked warehouse (so today's orders correctly deduct from it, per the user's own description) — the party is who it came from, recorded via `supplierId`, not where it now sits.
- **Schema (`purchase_entries`, additive/nullable, `drizzle/0005_stock_in_ledger.sql`):** `entry_date` (real-world "In Date", separate from `created_at`), `party_chalan_no`, `our_chalan_no`, `gst_percent`, `subtotal_amount`, `gst_amount` — `total_amount` (pre-existing) stays the final payable (subtotal+GST) so every existing Finance/Reports/Assistant query that already sums it as "what's owed" keeps working unchanged.
- **Auto-calculate, for real, both live in the dialog and authoritative on the server:** `modules/purchases/purchases.ts` computes subtotal (Σ qty×rate) → GST (×gst%) → payable server-side on every create/edit — never trusts a client-sent total. The dialog (`public/party.js`) mirrors the same formula live on `input` for instant feedback, matching the real sheets' own layout exactly (they compute the same three numbers, just as static values that go stale the moment a row changes).
- **Edit is not a plain UPDATE when qty/rate/SKU changes** — current stock is `SUM(delta)` over the ledger, not a mutable counter, so `updatePurchaseEntry` reverses the old effect (`MANUAL_ADJUSTMENT` of −oldQty) and applies the new one (`PURCHASE_RECEIPT` of +newQty), both referencing the entry, before touching the row — the audit trail always shows exactly what changed. **Delete** does the same in reverse (−quantity) before removing the entry, and un-links (not deletes) any `party_payments` recorded against it, matching the column's existing `onDelete:"set null"`.
- **The "Total To be paid Balance" running total is never stored** — every real sheet's own version of this column is a static value that silently goes stale the instant an earlier row is edited or deleted (exactly the failure mode this feature exists to fix). `listPurchaseEntries` computes it live with a SQL window function (`SUM(total_amount) OVER (PARTITION BY supplier_id ORDER BY entry_date, id)`), so it's always correct no matter how many entries changed after the fact. Paid/balance-due is likewise derived live from `party_payments` (reusing Finance's existing `POST /finance/payments`), not a static "Paid?" flag.
- **New CSV parser (`src/ingestion/parsers/stockIn.ts`) for the "MASTER STOCK SHEET" family — the 4 real files do NOT share one column set** (APL: `Chalan no.`/`Remark`/`Paid Date`/`Balance Dues`; Shivam & AK Enterprises: `Party Chalan no.`/`Our Chalan no.`/`Bill.no.`/`Bill Date`/`Paid Date`/`Remark`; JK: `Remark`/`Paid Date`/`Paid` where **`Paid` is a number**, not a status word) — so it parses by normalized header-name lookup with per-field alias lists, not fixed column positions, and recomputes every money figure from qty×rate rather than trusting the sheet's own (running, easily-stale) Total/GST/Balance columns.
- **Two real parsing bugs found and fixed during verification against the real files, not shipped on synthetic data:**
  1. **Glued day+month dates with no separator** (`"12June"`, `"29May"`, real cells in the AK Enterprises sheet, vs. every other row's `"12 June"`/`"29-May"`) made the date parser return `null` — caught by noticing 5 imported entries had a null `entryDate` and were silently sorting to "today" at the top of the ledger instead of their real 2026 date. **Fixed** by inserting the missing space before a leading digit-run/letter-run boundary before splitting.
  2. **"Paid Date" sometimes carries a status word instead of a date** (real AK Enterprises cells: `"PAID"`, `"PANDING"`, `"PAIDING"` typed straight into that column, with Remark left blank) — a naive date-parse-or-drop would have silently thrown away the only record that those 3 bills were paid. **Fixed**: when the "Paid Date" cell fails to parse as a date, its raw text is folded into the same paid-flag signal as Remark (so `"PAID"` still marks the bill paid); `"PANDING"`/`"PAIDING"` don't match the word-boundary `paid` check and correctly fall through as not-confidently-paid rather than guessed.
  3. **Disclosed, not a bug — JK's numeric "Paid" column sometimes exceeds that row's own bill total** (e.g. a ₹241.50 bill against a recorded `Paid` of ₹9,366, remark "Advance") — these are real lump-sum advance payments the party sheet recorded against whichever row was current that day, not a per-bill overpayment. Imported faithfully as-is (the payment amount as given, linked to that entry) rather than capped/guessed — correct in aggregate at the party level (Finance's supplier ledger sums payments across all of a party's entries), even though one row's own "Paid" figure can look like an overpayment in isolation.

- **User question (verbatim, Hinglish):** "MEESHO SE YE FILE AATI HAI TRACKING KE LIYE PDF ME TO ISKO KESE KARENGE" (Meesho sends this file for tracking, in PDF format — how do we handle it), alongside 4 real Meesho "Supplier Manifest" PDFs.

Whichever is given is converted to the same `{rawOrderNo, awb, carrier}` row shape before falling into the ONE shared matching/upsert loop — the order-matching logic itself was not duplicated per format. A row's label in the response is now `"page N — <subOrderNo>"` for a PDF row (vs `"row N"` for a CSV row) so errors stay traceable to source. A parse failure on a corrupted/non-PDF upload is caught and turned into a clean 400 (see verification below — this was a real bug caught during testing, not a hypothetical).
  - `public/app.html` + `public/app.js`: the Upload AWB / Manifest dropzone now accepts `.pdf` alongside `.csv`; a PDF is read client-side as base64 (`FileReader.readAsDataURL`, stripping the `data:...;base64,` prefix) and posted as `pdfBase64`, a CSV still posts as plain text `csv`, unchanged.
